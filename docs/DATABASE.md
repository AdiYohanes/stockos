# StockOS Database Design

Status: target design confirmed 2026-10-09; not implemented. PostgreSQL on Supabase. No executable SQL or migrations are included. Business vocabulary: [Glossary](../GLOSSARY.md). Contracts: [API_CONTRACT.md](API_CONTRACT.md).

## 1. Scope and Authority

One shop, one owner, integer base-unit stock, IDR only. Products and Inventory read the same product balance; Dashboard/Reports aggregate it. There is no tenant, warehouse, reservation, purchasing lifecycle, staff membership, sale/payment, expense, or supplier-management table.

Use PostgreSQL native constraints, row locks, transactions, and exact `numeric` arithmetic. Supabase JS/SSR clients handle auth and database RPC access; no ORM or generic repository framework is required. Dependencies are selected/installed only during separately authorized implementation.

The current balance is stored with the product for inexpensive reads. Append-only inventory events explain every quantity/cost change and reconcile to the stored balance; they are not an asynchronously applied event-sourcing system.

## 2. Common Representation

- Domain IDs and request IDs: UUID. Singleton IDs: small integer constrained to `1`.
- Quantities: PostgreSQL `bigint`, constrained to 0–1,000,000,000. Mutation quantities are positive integers; zero opening quantity and zero-difference counts are permitted.
- Selling price and purchase-total inputs: whole IDR, 0–1,000,000,000,000, stored exactly. No binary floating-point cost calculation.
- Current inventory cost value: `numeric(30,6)`, nonnegative, at most 1,000,000,000,000,000,000,000 per product. Zero stock implies zero cost value.
- Mean cost is derived from current cost value / current quantity; do not store an independently editable mean. Display average to six decimals when needed; never reconstruct inventory value from its rounded display average.
- Decimal DTO values are decimal strings without grouping separators; input whole-money strings have no decimal point. Version values are decimal integer strings. Quantities remain safe JavaScript integers within the chosen bound.
- Timestamps: `timestamptz`, generated by server/database, exported as ISO 8601 UTC. No backdating input.
- Text is trimmed at input. Names/category/supplier: maximum 120 characters; shelf 80; unit 30; barcode 64; reference 120; notes/reasons 1,000; description 2,000. SKU: 3–64 uppercase ASCII letters/digits plus `-`, `_`, `.`, `/`; normalize trim/uppercase before uniqueness checks.
- State versions are monotonic `bigint`; return as strings and never permit client assignment.

These bounds are technical guardrails, not a product forecast. Over-limit requests fail validation without partial writes. Expand only with matching schema/contract tests.

## 3. Relations

### `shop_settings` — exactly one shop

| Field | Type / rule |
| --- | --- |
| `id` | Singleton primary key `1` |
| `name` | Required nonblank text, max 120 |
| `address`, `phone`, `owner_name` | Optional profile text; max 500 / 40 / 120 |
| `timezone` | One of `Asia/Jakarta`, `Asia/Makassar`, `Asia/Jayapura`; default `Asia/Jakarta` |
| `default_unit` | Nonblank base-unit label, default `Pcs`; no fractional conversion |
| `default_min_stock` | Integer in quantity range, default 15; applied to new products only |
| `version` | Monotonic settings revision, initially 1 |
| `created_at`, `updated_at` | Server timestamps |

IDR and weighted-average costing are invariant behavior, not editable settings. Language/date-format/theme conveniences remain browser-local with resilient storage handling; reset never clears operational data. No notification, expiry, negative-stock, or reorder-prediction flags are persisted.

### `owner_registration` — protected bootstrap state and owner binding

| Field | Type / rule |
| --- | --- |
| `id` | Singleton primary key `1` |
| `state` | `unclaimed`, `provisioning`, or `bound` |
| `attempt_id` | Nullable unique server UUID; present during provisioning/binding |
| `email` | Nullable normalized candidate email, max 254; private |
| `auth_user_id` | Nullable unique FK to Supabase `auth.users`, delete restricted once bound |
| `provisioned_at`, `bound_at`, `updated_at` | Server timestamps as state requires |

Only trusted bootstrap server/admin code changes this row. Business access requires `state=bound`, session subject equals `auth_user_id`, and provider-confirmed email. `bound` prevents further owner signup even if the email is still awaiting confirmation.

A row-lock/compare-and-set claim commits before the provider call; do not hold a DB transaction open over email/network operations. The claim is not automatically reassigned on timeout. A definitive provider rejection that proves no user was created may compare-and-set only that attempt back to unclaimed. Ambiguous failures retain provisioning. A retry with the same setup secret and candidate email resumes/reconciles the same attempt; a different email is rejected as pending. Operator recovery checks provider state before resetting an unbound slot. Store no password, setup secret, verification token, or recovery token here.

### `products` — metadata and authoritative stock/cost balance

| Field | Type / rule |
| --- | --- |
| `id` | UUID PK |
| `sku` | Normalized SKU, unique across active and archived products |
| `name`, `category`, `unit` | Required nonblank text |
| `supplier` | Optional text; suggestions from existing values, not a supplier FK |
| `shelf_location`, `barcode`, `description` | Nullable optional text |
| `selling_price` | Whole IDR in input-money range |
| `min_stock` | Nonnegative integer in quantity range |
| `current_stock` | Nonnegative integer in quantity range; default zero |
| `inventory_cost_value` | Exact current cost value; default zero |
| `archived_at` | Nullable server timestamp; archive requires zero stock |
| `metadata_version` | Initially 1; increments for metadata edits/archive/reactivation |
| `stock_version` | Initially 0; positive opening makes it 1; increments for every inventory event, including cost-only and zero-difference opname |
| `created_at`, `updated_at` | Server timestamps |

Stock status is derived: quantity zero = out of stock; 0 < quantity <= minimum = low stock; otherwise in stock. Archive state is separate from stock health. No editable status, reserved stock, or independently maintained available stock.

SKU/base unit may change only before any inventory event exists. Receipt carton count and units per carton are input details, not another balance or an immutable conversion on the product. Carton size may vary per receipt without changing the base unit.

### `inventory_events` — append-only stock, count, and cost evidence

| Field | Type / rule |
| --- | --- |
| `id` | UUID PK |
| `product_id` | FK products, deletion restricted |
| `kind` | `opening`, `receipt`, `sold`, `opname`, or `cost_adjustment` |
| `stock_version` | Resulting product stock version; unique with product ID |
| `quantity_before`, `quantity_after`, `quantity_delta` | Integers; delta = after - before |
| `cost_before`, `cost_after`, `cost_delta` | Exact values; delta = after - before |
| `purchase_total` | Whole IDR, present for positive opening/receipt and found-stock opname from zero; otherwise null |
| `counted_quantity` | Present only for opname, including unchanged counts |
| `carton_count`, `units_per_carton` | Nullable positive integers, both present together for receipt/opening carton mode |
| `reference` | Receipt reference or generated opening/opname/sold/correction reference |
| `note` | Optional text; required for cost adjustment or linked quantity correction |
| `correction_of_event_id` | Optional FK to earlier event of the same product, deletion restricted |
| `actor_id` | FK provider user, deletion restricted; trusted session subject |
| `request_id` | Unique FK to successful mutation request |
| `sku_snapshot`, `name_snapshot`, `unit_snapshot`, `supplier_snapshot` | Original descriptive context; supplier nullable |
| `selling_price_snapshot` | Current price for audit only; not proof of paid revenue |
| `recorded_at` | Server timestamp |

Sold events require negative quantity delta; receipt/opening positive delta; cost adjustment zero delta. Opname accepts either delta sign or zero. Cost adjustment preserves quantity; zero-quantity products cannot receive positive cost value. Corrections never replace old rows. No UPDATE/DELETE grant for ordinary events.

No sales transaction is inferred from a price snapshot: sold quantity is manual inventory evidence, with no payment/discount/actual-sale-price record.

### `mutation_requests` — durable retry identity

| Field | Type / rule |
| --- | --- |
| `request_id` | Client-generated UUID PK, globally unique within this single shop |
| `actor_id` | Trusted owner subject |
| `operation` | Approved business mutation identifier |
| `payload_hash` | Server-computed digest of canonical normalized operation input, excluding secrets and request ID |
| `result` | Bounded success DTO needed to return original committed result |
| `completed_at` | Server timestamp |

Committed rows contain successes only. Request reservation, business writes, audit, and result commit in one transaction; failed requests roll back the reservation. After authentication and strict input normalization, a duplicate request with the same actor/operation/hash returns original success before checking current entity constraints, SKU uniqueness, archive state, or stale versions. A create-product replay must not fail because its own committed SKU now exists. Different payload/operation for a reused ID is a conflict. Do not hash raw object key order or client-supplied hashes.

Keep successful request identities while related audit/history is retained; no automatic expiry in first release. Concurrent identical submissions serialize on uniqueness and return the same result. No new stock operation is created during a replay.

### `administrative_events` — metadata/settings lifecycle evidence

UUID PK; `kind` (`product_created`, `product_updated`, `product_archived`, `product_reactivated`, `settings_updated`); optional product FK; owner actor FK; request FK; bounded changed-field before/after values; server timestamp. No secrets or provider credentials. Append in the same transaction as successful business mutation. An operation may have both administrative and inventory evidence, such as product creation with opening stock.

## 4. Cost Rules

Let Q be current quantity, C current inventory cost value, n received/sold units, P receipt purchase total. Round stored cost results to six decimal places using PostgreSQL exact numeric rounding (half away from zero).

- Receipt/opening: Q' = Q + n; C' = C + P. Mean becomes C'/Q'. Free goods are valid P=0. Selling price is unchanged unless separately edited.
- Sold: require n <= Q. If n=Q, consume all C and set Q'=0,C'=0. Otherwise consumed cost = round(C*n/Q,6); C' = C - consumed cost. This preserves final residual value without accumulating a second stored average.
- Opname from Q>0: Q' = counted quantity; C' = round(C*Q'/Q,6). Q'=0 sets C'=0. Same count stores an event without changing C.
- Opname from Q=0 to Q'>0: require whole-IDR `foundPurchaseTotal`; C'=that value. Do not reuse a stale historical price or infer purchase cost from selling price.
- Cost adjustment: for Q>0 require explicit whole-IDR replacement total current cost and a reason; Q unchanged. For Q=0 only zero total is allowed. Do not reprice historical sold events.
- Potential selling value = sum(current_stock * selling_price) for active products. Potential gross profit = potential selling value - sum(inventory_cost_value). Negative results are valid. Do not round each product before aggregation.

Examples to test: 10 units with C=30,000 plus 10 at P=40,000 yields Q=20,C=70,000, mean=3,500. Selling 5 consumes 17,500; 15 remain with C=52,500. Three units costing 10,000 sold individually consume 3,333.333333, 3,333.333334, and final 3,333.333333, leaving zero residual.

## 5. Transaction and Concurrency Boundary

Business mutations execute PostgreSQL functions via Supabase RPC under the verified owner's session. PostgreSQL owns exact arithmetic and transactions; separate HTTP database calls are not a transaction.

Each function verifies owner binding, validates allowed fields/limits, claims/replays request identity, locks relevant product/settings row, checks archive/version/quantity conditions, writes balances and evidence, stores result, then commits. Read committed isolation with explicit row locking suffices for these single-product operations; no premature cross-product batching.

- Receipt/sold operations apply against locked current balance; no client absolute balance write. Two sold requests for 4 units against Q=5 cannot both succeed.
- Opname/cost adjustment require expected `stock_version`. Metadata edits require expected `metadata_version`. Archive requires both revisions and locked zero stock; reactivation requires metadata revision. Stale errors leave all state unchanged.
- Creation, opening stock, event, administrative evidence, and retry record are one transaction. Zero opening quantity produces no inventory event; metadata creation is still audited.
- Product update DTO cannot write balances, history, actor, versions, or calculated modal values.
- Lock ordering is request identity then affected entity; keep ordering consistent. Deadlock/serialization failures roll back and may retry internally a bounded number of times with the same request ID.
- Returned success reflects the committed operation. On replay it is the original snapshot, so UI refreshes current data instead of treating old DTO as current truth.

## 6. Privileges and Indexes

Business tables live in a non-public schema. Enable RLS and revoke all direct table access (SELECT/INSERT/UPDATE/DELETE) from PUBLIC, anon, and authenticated. Expose narrowly scoped read/mutation RPCs with owner verification; explicitly revoke PostgreSQL's default PUBLIC function EXECUTE and anon access, granting only approved business RPCs to authenticated and bootstrap operations to trusted admin roles. Any SECURITY DEFINER function has a fixed safe search path, qualified identifiers, restricted EXECUTE grants, and no user-controlled SQL. Owner verification uses verified provider subject/email and singleton binding, never supplied actor IDs. It also checks the signed provider session identifier against a live, valid backing session using supported Supabase session metadata, so a revoked but unexpired access JWT cannot directly invoke RPCs. Reject absent/invalid session identifiers. Implement live-session lookup through a private SECURITY DEFINER helper with fixed safe search path and sufficient Auth-schema read privileges, not browser SELECT grants. Validate session-ID UUID syntax before casting; absent/malformed claims return authorization denial, not a raw SQL error. Verify the session belongs to the signed subject and enforce applicable expiry/revocation semantics in the foundation proof. Bootstrap uses separately granted admin-only functions without an owner session; no service-role bypass is added to ordinary business RPCs. Do not expose Auth session rows to browser roles. RLS is defense in depth, not a substitute for function checks.

Bootstrap/admin credentials are server-only and limited to owner provisioning/reconciliation. Normal business requests use session-scoped clients rather than bypassing RLS with service credentials. Public provider signup is disabled; directly registered/unbound provider users never gain shop access.

Indexes: unique SKU; product active/category ordering for actual list queries; product creation time plus ID; inventory events (product_id, recorded_at descending, id descending), (recorded_at descending, id descending), and kind/time for report queries; unique product/version; unique request ID; correction reference; administrative event time/product. Do not add full-text/trigram extensions until measured queries need them. Category/supplier suggestions use bounded distinct text queries.

## 7. Retention, Migrations, and Provider Recovery

Products with history are never hard-deleted through the app. Owner deletion/transfer, factory data wipe, historical rewriting, and retention automation are outside scope. Archive preserves foreign keys and SKU ownership. Passwords/sessions are managed by Supabase Auth, not duplicated here.

When implementation is approved: create versioned migrations with explicit schema/grants/functions, production-empty seeds (singleton defaults only), and forward/recovery procedures. No mock product/customer credentials in production seeds. Test migrations and restore in isolated nonproduction resources. Verify PostgreSQL function contracts under anonymous, unrelated-user, and owner credentials.

Auth provisioning and PostgreSQL cannot share a distributed transaction. Persist bootstrap attempt, create/invite one provider user server-side, bind that exact subject, and block other claimants. If provider call times out, reconcile the recorded attempt/email before retrying creation. Never clear claim/binding blindly; an unresolved attempt fails closed and displays setup-pending/retry guidance. Successful binding closes signup while email confirmation/password setup can be retried for that same subject.

The implementation must prove supported Supabase admin invitation/verification behavior with public signup disabled and a functioning email service before wiring the full signup UI. No fallback that enables public signup or bypasses email verification. Provider mail limits and delivery are operational gates, not assumptions.
